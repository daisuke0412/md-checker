# md-checker 概要・要件

md-checker を初めて読む人が最初に見る 1 枚です。「何のための道具で、何ができて、何をしないか」をここで把握できます。

## 1. md-checker とは

ローカルにある Markdown 文書群（技術ブログ・社内文書・開発ガイドなど）を対象に、**似た記載を見つけたり、過去の記載との矛盾を指摘したりする RAG 検索エージェント**です。

新しい記事や文書を書くとき、「前にも似た説明を書いていないか」「過去の記載と食い違っていないか」を機械的にチェックすることを目的とします。

## 2. 想定ユースケース

- 技術ブログや社内文書の作成時に、過去の記事に似た説明をしていないか検索する。
- 新しく書いた内容が、過去の記載と矛盾していないかをチェックする。

## 3. 機能

| # | 機能 | 説明 |
|---|------|------|
| ① | 類似記載の検索 | 似た意味の記載箇所を検索する（ハイブリッド検索：意味＋語彙） |
| ② | 矛盾の指摘 | 取得した記載と、チェック対象の主張が矛盾していないかを AI（LLM）に判定させる |
| ③ | LLM 出力評価 | チェック時の LLM 判定を後から別の LLM（評価者）に採点させる（LLM-as-judge） |

## 4. 全体の流れ

```
[構築フェーズ（事前処理・1回）]
  resources/target_mds/ の .md → チャンク化 → ベクトル化 → vector_store.json に保存

[検索フェーズ（クエリのたび）]
  クエリ（テキスト直接入力）
    → ベクトル検索（意味） ＋ BM25（語彙）
    → RRF で統合 → 上位 k 件の候補
    → LLM がツールループで能動的に追加検索しながら判定（機能①: 類似 / 機能②: 矛盾）
    → LLM の入出力ペアを logs/checker/ に記録

[評価フェーズ（任意・後からまとめて）]
  logs/checker/ の LLM 入出力ログ
    → 別の LLM（評価者）が 1 ペアずつ採点（機能③: LLM-as-judge）
    → 採点結果を logs/judge/ に保存
```

詳細は [architecture.md](architecture.md) を参照。

## 5. 機能要件

- **① 類似記載の検索**: チェックしたい文章を直接入力すると、意味・語彙の両面で関連する既存チャンクを上位 k 件返す。
- **② 矛盾の指摘**: 取得した候補チャンクとチェック対象の主張を突き合わせ、矛盾の可能性がある箇所を指摘する（LLM による判定）。

入力はテキスト直接入力のみ（最大 1200 文字）。1 入力＝1 クエリ＝1 エージェントループ。

- **③ LLM 出力評価**: チェック時の LLM 入出力を後からまとめて別の Claude に採点させる。正解データ不要の reference-free 評価（出典の実在性・引用の実在性・判定の妥当性・取りこぼしを評価）。採点呼び出し自体はチェックのログに混入しない（`log_to_eval=False` による経路分離）。

詳細は [architecture.md](architecture.md)・[design/agent.md](design/agent.md)・[design/eval.md](design/eval.md) を参照。

## 6. 非機能要件・前提・制約

| 項目 | 内容 |
|------|------|
| 対象規模 | Markdown ファイル数は **50 個未満**を想定（現状チャンク数の目安は数十〜百件規模） |
| 実行環境 | まずは**ローカルで完結**して動くこと |
| ベクトルストア | 専用 DB を使わず、**ローカル JSON（`vector_store.json`）**で簡易に持つ |
| 埋め込み・検索・判定 | 埋め込みは Voyage、矛盾判定は Claude（Anthropic API） |
| コスト | 埋め込みは構築時 1 回のみで激安。検索時のコストは候補チャンク × k 件分の入力トークン |

## 7. スコープ外（現時点）

- 大規模文書（数千ファイル）への対応。増えて遅くなったらベクトルストアを差し替える方針。
- リアルタイムの自動再構築（ファイル監視）。現状は手動で再構築する。
- ファイル単位入力（Markdown ファイルまるごとチェック）。現状はテキスト直接入力のみ。
- Web UI。現状は CLI／スクリプトでの利用を想定。
